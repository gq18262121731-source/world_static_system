# 技能 1：T10 手环原始数据可信接入——完整版 5 分钟讲稿与操作手册

## 1. 本段展示目标

时间：总流程的 `05:00–10:00`，净时长 5 分钟。

本段只回答一个问题：**如何把手环采集器输出的原始十六进制帧，转换为可追溯、可判定质量、可实时进入平台的标准健康数据。**

本段不讲健康评分、SOS、Hot Fix、告警策略或 Agent 推理。协议依据为根目录《体温心率手环数据解析说明 V3.0》：广播包直接携带心率、血氧和体温；回应数据因长度受限拆成 A/B 两包，并以约 1 秒间隔轮流发送，通过 `0x1803 / 0x0318` 区分。

## 2. 人员与屏幕分工

| --- | --- | --- |

| 1 号 | 只在核心编码段解释设计意图 | 不逐行念代码，不抢操作口令 |

建议屏幕布局：主屏预开三个页签——`终端 A：原始帧`、`IDE：demo_t10_protocol_skill.py`、`网页：实时体征卡片`；终端 B 在后台运行健康 WebSocket 监听。B 机负责手环、双采集器和键盘特写。

## 3. 上台前 30 分钟检查

### 3.1 必须核对的真实设备信息

1. 手环屏幕/标签 MAC、平台注册设备 MAC、网页当前选中设备和命令参数必须完全一致。
2. 当前仓库存在一处必须人工核准的配置差异：`shouhuan.py` 注释及多数测试使用尾号 `DF`，但 `HANDWARE_MAC` 常量为尾号 `DC`；注释写自动探测 `COM3`，常量为 `COM12`。本演示不自动采用其中任意一个结论。
3. 两个采集器分别记作：采集器 A（技能终端）和采集器 B（平台常驻链路），记录实际 COM 号。
4. 同一个 COM 口不能同时被后端和技能脚本打开。若只有一个采集器，就让后端独占串口，技能代码改用备用录制帧做解析展示；效果验证仍以平台已有实时链路为准。

查看串口：

```powershell
conda run -n helth python -c "from serial.tools import list_ports; [print(p.device, p.description, p.hwid) for p in list_ports.comports()]"
```

### 3.2 赛前测试

```powershell
conda run -n helth python -m pytest tests/test_demo_t10_protocol_skill.py tests/test_serial_parser.py tests/test_serial_reader.py -q
```

启动平台后，在终端 B 监听与网页相同的设备：

```powershell
conda run -n helth python scripts/diagnostics/watch_health_ws.py --device-mac 54:10:26:01:00:DF
```

终端 A 的实时原始帧命令（把 `COMx` 和 MAC 换成现场核准值）：

```powershell
conda run -n helth python scripts/demo_t10_protocol_skill.py --mode serial --phase capture --port COMx --device-mac 54:10:26:01:00:DF --max-frames 6
```

核心解析与平台推送命令：

```powershell
conda run -n helth python scripts/demo_t10_protocol_skill.py --mode serial --phase pipeline --port COMx --device-mac 54:10:26:01:00:DF --stop-after-complete --push-url http://127.0.0.1:8000/api/v1/health/ingest --verify-platform
```

只有在采集器 A 尚未正确配置、且明确知道该设备允许写入持久化 AT 参数时，才追加 `--configure-collector`。该开关会执行 `AT+SCANSTOP → AT+MAC → AT+TYPE=5 → AT+SCANSTART`，采集器参数可能在断电后仍保留。

备用录制帧命令：

```powershell
conda run -n helth python scripts/demo_t10_protocol_skill.py --mode offline --phase pipeline --device-mac 54:10:26:01:00:DF --stop-after-complete
```

该命令首屏会固定显示 `备用录制帧（非实时）`，不能口头省略这一事实。备用模式不推送到正式串口设备，避免把录制帧伪装成实时数据。

### 05:45–06:30｜方案设计（45 秒）

**05:45–05:57｜2 号**

[主屏显示单行流程：`串口行 → 包型识别 → 字段解析 → A/B 时间窗融合 → 标准化 → 质量标记 → API/WebSocket`。]

“我们的处理链路只有七步。先从串口噪声里提取 MAC 和 BLE payload，再根据协议标记识别包型。广播包可直接解析；回应包则必须处理 A、B 两段。”

**05:57–06:12｜2 号**

[指向流程图中 `A/B 时间窗融合`。]

“协议规定，回应数据受长度限制，以约一秒间隔轮流发送。`0x1803` 的 A 包提供心率、血氧、电量、表面温度和步数；`0x0318` 的 B 包补充血压和体温。我们按设备 MAC 建短时缓存，只融合时间窗内的配对包。”

**06:12–06:25｜2 号**

“融合后统一成标准对象，同时保留原始 A/B 包作为证据。字段缺失或越界时，我们只写质量标记并保留 `null`，绝不为了页面好看伪造一个正常值。在本次演示入口中，只有质量完整的数据才进入现有平台接口。”

## 5. 成功判据

现场必须同时满足以下条件：

1. 原始终端出现来自真实采集器的 HEX；若使用备用模式，屏幕明确显示“备用录制帧（非实时）”。
2. `PACKET_IDENTIFIED` 先后出现 `response_a` 与 `response_b`，或真实固件对应的合法包型。
3. 最终 `STANDARDIZED` 同时出现非空的 `heart_rate`、`spo2`、`temperature` 和 `quality`。
4. A 单包显示 `partial`，A/B 融合后显示 `complete` 和 `source_packets: [response_a, response_b]`。
5. `PLATFORM_PUSH.status` 为 `accepted`；启用校验时，`PLATFORM_VERIFY.status` 为 `matched`。
6. 网页、移动端和终端使用同一 MAC，三项体征数值一致。

## 7. 评委追问的 20 秒答法

**为什么不直接在前端解析？**

“协议解析、跨包缓存和质量判定必须在统一后端完成，否则网页和移动端会产生不同口径；前端只消费标准对象。”

**为什么 A 包已经有心率血氧还不直接算完整？**

“本次展示定义的是回应包完整测量。A 包可作为部分观测，但血压和 B 包体温未到之前标记为 `partial`，下游能明确选择是否使用。”

**`spo2` 和项目里的 `blood_oxygen` 是否冲突？**

“不冲突。`spo2` 是舞台标准对象的可读别名；进入既有接口时显式映射为 `blood_oxygen`，接口没有改字段，所以旧前端完全兼容。”

**质量标记会不会把真正异常的老人数据丢掉？**

“不会。质量判定只检查包是否完整、字段是否缺失以及传感器硬边界，不把医学上的高低当作采集错误；健康风险由后续模块判断。”
